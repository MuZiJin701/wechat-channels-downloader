# Spec：微信视频号下载便携式 TUI

本文根据已有讨论整理，描述目标行为。测试边界已由用户确认，已发布为 [Spec #1](https://github.com/MuZiJin701/wechat-channels-downloader/issues/1)。规格形成时尚无应用代码或平台验收结果；当前实现与验证情况见 [README](../README.md)。

## Problem Statement

用户希望直接下载微信视频号分享链接对应的内容，包括视频型动态和图文动态。目前已有实现涉及元宝登录态维护、解析服务、平台相关脚本及下载流程，普通用户仍需处理运行环境、登录凭据和工具组合，无法在 Windows、Linux、macOS 上通过双击一个便携程序完成操作。

需要把已存在的“元宝登录态 → 视频号解析 → 媒体下载”原理整合为本地 TUI：程序自行检查登录态，需要时展示微信二维码，随后接受视频号分享链接并保存对应内容。用户不需要安装 Python、手工复制 Cookie 或维护远程解析服务。

## Solution

项目名称为“微信视频号下载”，英文标识为 `wechat-channels-downloader`。分别提供各目标平台的便携包和双击启动入口，随包携带 Chromium。

用户双击启动后，程序通过 Playwright 驱动无头 Chromium 检查元宝登录态。已有登录态有效时复用；缺失或明确过期时，在 TUI 展示可由微信扫描的二维码，等待用户完成元宝登录。确认登录成功后保存可复用的登录态，再展示分享链接输入框。

输入接受 `https://weixin.qq.com/sph/...` 形式的视频号分享链接。程序按既有解析原理取得内容并下载：视频型动态保存视频；图文动态保存全部图片及可取得的文字内容，保持图片顺序。TUI 显示当前阶段、成功结果与保存位置，失败时给出可理解的原因。

采用便携存储：启动程序旁的 `data/` 保存登录态，`downloads/` 保存下载内容；macOS 在 `.app` 外侧保存数据，保持应用包内部不变。目录不可写时明确报错。

| 目标系统 | 架构 | 计划验收方式 |
| --- | --- | --- |
| Windows 11 | x64 | 本机自动检查与真实扫码、下载验收 |
| Ubuntu 24.04 | x64 | GitHub Actions 构建、打包产物启动与自动化流程 |
| macOS 14+ | Apple Silicon | GitHub Actions 构建、打包产物启动与自动化流程 |
| macOS 14+ | Intel | GitHub Actions 构建、打包产物启动与自动化流程；明确实际覆盖的系统版本 |

## User Stories

1. 作为 Windows 用户，我希望双击便携程序即可打开 TUI，以便直接使用下载工具。
2. 作为 Linux 用户，我希望获得适配目标桌面系统的双击启动入口，以便无需手工输入启动命令。
3. 作为 macOS 用户，我希望获得能启动终端界面的程序入口，以便用相同流程完成下载。
4. 作为 Intel Mac 用户，我希望取得适合本机架构的包，以便正常运行程序和 Chromium。
5. 作为 Apple Silicon Mac 用户，我希望取得适合本机架构的包，以便正常运行程序和 Chromium。
6. 作为普通用户，我希望运行包包含所需应用运行环境，以便无需安装 Python。
7. 作为普通用户，我希望 Chromium 随包提供，以便无需另外安装浏览器或驱动。
8. 作为用户，我希望启动后自动检查元宝登录态，以便知道是否需要登录。
9. 作为已登录用户，我希望有效登录态自动复用，以便不必每次重新扫码。
10. 作为尚未登录的用户，我希望在 TUI 看到可扫描的微信二维码，以便完成元宝登录。
11. 作为登录态过期的用户，我希望程序提示重新扫码，以便恢复下载能力。
12. 作为扫码用户，我希望登录成功后程序自动进入链接输入阶段，以便无需复制 Cookie。
13. 作为扫码用户，我希望二维码过期、登录失败或额外验证要求得到明确提示，以便理解当前状态。
14. 作为用户，我希望仅在登录成功得到确认后保存登录态，以便下一次能够可靠复用。
15. 作为用户，我希望网络故障与登录态过期被区分，以便临时断网不会破坏原有登录态。
16. 作为用户，我希望粘贴视频号分享链接到输入框，以便直接指定需要下载的内容。
17. 作为用户，我希望不支持的链接格式得到明确提示，以便及时纠正输入。
18. 作为用户，我希望视频型动态保存为完整的视频文件，以便离线观看。
19. 作为用户，我希望图文动态也能下载，以便工具覆盖已讨论的两种内容类型。
20. 作为图文下载用户，我希望同一动态的全部图片都被保存，以便内容不被遗漏。
21. 作为图文下载用户，我希望图片保持原有顺序，以便按发布顺序浏览。
22. 作为图文下载用户，我希望可取得的文字内容一并保存，以便保留图文表达。
23. 作为图文下载用户，我希望没有文字的动态也能正常保存图片，以便正常处理纯图片内容。
24. 作为用户，我希望解析失败或内容失效时看到明确结果，以便知道下载为何无法完成。
25. 作为用户，我希望 TUI 显示登录、解析与下载阶段，以便确认程序正在处理任务。
26. 作为用户，我希望完成后看到保存位置，以便找到视频、图片和文字。
27. 作为用户，我希望中断或失败的下载不被标为成功，以便区分完整内容与残留文件。
28. 作为用户，我希望失败处理不会损坏已经下载好的文件，以便保留已有内容。
29. 作为便携版用户，我希望登录态存放在程序旁，以便程序与数据集中管理。
30. 作为便携版用户，我希望下载内容存放在程序旁，以便按约定找到输出。
31. 作为便携版用户，我希望保存位置不随启动时的工作目录改变，以便通过不同入口启动时结果一致。
32. 作为 macOS 用户，我希望数据存放在应用包外侧，以便保持应用包内部完整。
33. 作为用户，我希望目录不可写时得到明确错误，以便调整程序所在位置。
34. 作为用户，我希望登录态不会出现在终端日志、公共仓库或 CI 产物中，以便保护账户会话。
35. 作为维护者，我希望项目名称聚焦微信视频号下载，以便用户理解用途，而元宝仅作为实际登录与解析依赖说明。
36. 作为维护者，我希望 Windows 本机验证真实扫码、登录态复用、视频下载和图文下载，以便确认完整业务可用。
37. 作为维护者，我希望 Linux 与 macOS 在 GitHub Actions 验证实际打包产物和 Chromium 启动，以便发现平台适配问题。
38. 作为维护者，我希望测试报告区分模拟流程、真实业务和桌面操作，以便不把未执行的验收误报为通过。
39. 作为维护者，我希望自动化使用临时登录态和模拟外部服务，以便不依赖真实账户或对外发送敏感数据。

## Implementation Decisions

- 新项目独立于讲座预约工具，保留“微信视频号下载”的产品名称与英文标识；元宝只在登录与解析的技术说明中出现。
- 交互以 TUI 的完整下载用例为主线，串联登录态检查、必要的二维码登录、链接输入、内容解析与落盘；界面必须能够接收输入并反映当前阶段。
- 使用 Playwright 驱动 Chromium 无头模式，复用已有浏览器生命周期管理经验以及视频号笔记项目的扫码和解析原理。实际需要保存的认证数据由验证确定，不先假设 Cookie 是登录态的全部。
- 先检查已有登录态，确认有效后复用；只有缺失或明确失效才要求扫码。网络故障、限流或服务错误不等同于登录态过期，不因这类故障覆盖有效的旧状态。
- 登录页面需要等待异步呈现的微信登录弹窗；自动弹窗已出现时直接使用，避免点击被它遮挡的首页入口。退出后应恢复原有终端属性，恢复操作放在 Playwright 子进程清理完成之后。
- 扫码成功必须通过元宝身份检查或等效的真实认证结果确认；仅显示二维码、页面跳转或取得非空 Cookie 都不代表登录成功。失败时保留旧的可用状态。
- 登录和解析在用户本机完成，不要求部署第三方解析网关。沿用元宝解析分享链接、取得视频号内容信息、下载媒体的既有链路，不把讲座系统的学校登录逻辑当作元宝实现。
- 以解析结果识别视频型动态和图文动态；视频下载媒体文件，图文下载全部图片并保存可取得的正文。图文不能降级为只下载首图，也不增加 OCR 或笔记生成步骤。
- 分享链接是外部输入，只接受已讨论的视频号分享链接形态；不得把携带登录态的解析请求发送到用户任意指定的服务地址。
- 下载失败不报告成功，不把不完整文件当作完成结果，也不破坏已经存在的完整文件。具体重名策略和内部临时文件组织不预先固定。
- 遵守已确定的便携存储决策：从应用实际位置确定数据位置，保持登录态与下载内容分开；目录不可写时明确失败，不静默改存到系统用户目录。
- 各目标系统和架构分别构建交付包与双击启动入口，携带应用运行环境及 Chromium。适配原参考入口中的 Linux 文件锁、固定 Linux 二进制路径及不适用于 Windows 普通终端的输入处理。
- 登录态属于敏感数据，不写入日志、公开仓库或 CI 产物。新增候选登录态应验证后安全替换，保存失败时不得损坏原有可用状态。
- 当前没有可复用的本项目应用模块或测试入口；实现时采用能满足完整用例的最小结构，TUI 框架、实现语言、打包器与解析器封装方式不视为已有讨论确定的选型。

## Testing Decisions

- 用户已确认一个主测试边界：从 TUI 的完整用户流程验证“登录态检查／扫码提示 → 链接输入 → 解析 → 视频或图文落盘”。优先观察界面结果、保存位置和文件内容，不以内部函数调用次数、私有状态或模块划分作为断言。
- 在这个边界内覆盖交互编排、真实 Playwright／Chromium、登录态持久化、内容解析和下载结果。自动化仅模拟元宝、微信与媒体服务等外部响应；使用真实 Chromium 和临时文件目录，隔离外网，不加载真实凭据。
- 当前新仓库没有应用或测试。可借鉴讲座预约项目中使用临时配置、隔离浏览器页面并阻断外部请求的测试方式；参考项目的上游验收记录只作为实现线索，不作为本项目的通过证据。
- 登录场景覆盖有效状态复用、状态缺失、明确过期、扫码成功、二维码过期、额外验证或登录失败，以及网络错误不误删旧状态。断言登录阶段转换、可复用状态及错误结果，而不是特定网页内部结构。
- 内容场景覆盖视频文件完整落盘、多图及文字保存、图片顺序、无正文图文、错误链接、解析失败及内容不可用。断言实际输出与成功／失败结果。
- 文件与凭据场景覆盖应用位置与当前工作目录不同、目录不可写、下载中断、保存状态失败、既有完整文件不被破坏，以及输出日志中没有测试用敏感值。所有写入限定在临时目录。
- Windows 11 x64 在本机验证实际交付包和双击入口，由用户参与真实微信扫码，验收首次登录、重启后登录态复用，以及至少一条视频型动态和一条图文动态的完整下载；本规格发布时尚未执行这些操作。
- Linux 和 macOS 使用 GitHub Actions 验证对应架构构建、便携包启动、包内真实 Chromium 无头启动与上述自动化流程；不能只运行源码测试而不检查打包产物。
- Linux 服务器实机排查后补充：模拟延迟自动登录弹窗与主动打开登录入口两条 TUI 流程；Linux/macOS 使用真实 PTY 验证源码及打包入口启动浏览器、Ctrl+Q 退出后完整恢复终端属性。Windows 跳过该 POSIX 检查，不以跳过作为通过证据。
- CI 不上传个人登录态，不等待无人可完成的真实扫码。不具备人工扫码和桌面验收条件时，将真实元宝扫码、线上完整下载和文件管理器双击体验明确标注为未验证，而不是报告通过。
- 测试结果列明实际操作系统版本与架构。macOS Intel 在较新系统上的 CI 通过不能替代最低目标系统的实际验收；未覆盖的最低版本保持明确的验证缺口。

## Out of Scope

- 学校讲座预约业务、学校账号登录及其部署配置。
- 任意小程序链接、非视频号站点、批量队列与直播录制；本规格覆盖已讨论的单条视频号分享链接中的视频型动态与图文动态。
- OCR、ASR、内容总结、笔记生成、转码及编辑功能。
- 多账户管理、云端同步、托管解析服务和自动更新等未讨论的附加功能。
- 自动绕过微信或元宝的安全验证；额外验证要求应明确提示，不自动切换到未约定的登录流程。
- 收费分发方案及其许可谈判；它们不是本次规格形成的前置问题。
- 将自动化或上游自述替代真实业务验收，或承诺所有 Linux 发行版、系统版本与架构均已兼容。
